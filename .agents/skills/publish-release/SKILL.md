# 正式发布

仅在当前项目根目录执行。正式发布包含更新日志、一次本地提交和经确认后的 GitHub 推送。

## 准备发布

1. 运行 `git status --short`。没有变更时说明“没有需要发布的内容”，停止。
2. 如果用户未提供版本号，先询问目标版本号；不要自行决定 SemVer 版本号。
3. 检查待提交文件，禁止暂存密码、Token、密钥、`.env`、本地配置或其他敏感内容。发现疑似敏感文件时停止并说明文件名。
4. 更新 `CHANGELOG.md` 中目标版本的内容。只记录玩家能感知到的新功能、优化和 Bug 修复；不要记录代码整理、变量改名或内部重构。保留发布日期字段。
5. 阅读变更摘要，生成一条规范简洁的中文提交说明。
6. 运行必要的项目检查。检查失败时停止，不提交。
7. 暂存本次发布需要的文件并执行 `git commit`。不使用 amend，不改写已有历史。

## 推送前确认

1. 在执行 `git push` 前展示待推送内容摘要、commit message、commit hash 和目标分支。
2. 等待用户明确回复“确认发布”。在收到前严禁推送。
3. 检查 GitHub 与 Netlify 自动部署关联：检查 `netlify.toml`、`.netlify`、GitHub Actions、仓库部署设置及其他可验证线索。
4. 如检测到关联，说明此次 push 可能触发 Netlify 部署并消耗 Credits，等待用户再次明确确认后再推送。
5. 严禁使用强制 push。推送后验证远程分支，并报告 commit hash、推送分支和 push 是否成功。

## 安全规则

- 不执行 `git reset`、`git rebase`、`git clean`、`git stash pop`、强制 push 或任何改写 Git 历史的操作。
- 不删除文件。
- 未经用户明确确认，绝不执行 `git push` 或线上部署。

## 更新日志时间边界

- 每次发布只记录上一个已发布版本之后发生、并且玩家能够感知到的新增功能、优化和 Bug 修复。
- 发布前先确认 CHANGELOG.md 顶部的上一个版本号，再以该版本的提交时间为边界检查本次变更；不得把更早版本已经发布过的内容重新写入新版本。
- 如果工作区混有多个版本周期的修改，只记录本次发布实际包含且尚未在 CHANGELOG.md 记录过的内容；无法确认归属时暂停并说明，不凭猜测补写历史。
