# 开发规范

## 修改原则

- 最小修改：只改完成任务所需的文件和逻辑。
- 影响分析：修改前搜索入口、调用方、配置 ID、存档字段、UI 选择器和测试。
- 保持兼容：模块 `id`、`shareCode`、配置码格式、航程码字段和旧模式行为未经确认不得破坏。
- 保持可运行：每次修改后至少能通过本地服务器加载主菜单；不能把测试代码、临时开关或调试日志带进正式路径。
- 模块化：新增内容优先配置化、复用现有 behavior；避免把所有规则塞进 `Game.js`。
- 可扩展：新增模块不应要求在 `Player`、主循环和 UI 各处增加同构特判，除非它确实是新系统边界。
- 避免硬编码：关卡、敌机、环境、奖励和技能数值应放在对应 `src/config/`。
- 不为修一个问题破坏其它模式；普通、躲避、教程和光锥之外必须分别检查。
- 不进行无意义重构；如果必须重构，先说明收益、影响面和回滚方式。
- 兼容性采用轻量冒烟标准：用户已确认的 GitHub 部署版本在手机和电脑正常运行；除非出现真实复现问题或用户另行要求，不建立复杂设备矩阵和性能预算。

## 工作区与文件归属

- 任务开始先执行 `git status --short`、`git diff --name-only` 和必要的逐文件差异检查。
- 开始任务前已经存在的修改默认属于用户；必须在任务记录或交接说明中列出，并默认排除出本次修改和提交。
- 提交时使用明确的任务文件列表，不使用 `git add -A`。
- 如果任务必须修改已有用户修改的同一文件，先暂停并说明冲突范围；得到用户确认后才可合并。无法可靠分离时必须停止。

## 代码与资源边界

- 不新增 npm 依赖或构建链，除非用户明确批准架构变化。
- 不直接编辑 `publish-package/` 或 ZIP；它们是生成物。
- 不把外部图片、音频或字体默认为必需资源；如果加入，必须提供加载失败后备。
- 暂停开发的内部代码可以保留以便维护，但不得把原型敌机、旧合成定义或备份模块写成玩家当前可用内容；当前没有“合成模块”这一玩家定义。
- 不修改模块和存档标识以“整理命名”；先评估已有配置码/航程码。
- 不生成无意义 BAT；PowerShell 脚本应有明确的可复现用途。

## 测试规范

1. 先运行 `node --check` 检查本次涉及的 JS。
2. 使用 `start-server.ps1` 打开主页面和 `tests/index.html`。
3. 检查浏览器控制台错误、主菜单、改装、至少一个普通战斗、暂停/恢复和返回流程。
4. 涉及触摸、布局、UI 或输入时，补做鼠标、键盘、触摸/移动端检查。
5. 每次正式发布前，无论本次改动是否涉及 UI，都必须完成一次手机端触控回归；至少验证主菜单、改装界面机库按钮、弹窗按钮、触摸拖动和技能按钮，并记录实际结果。
6. 涉及模式/存档/模块/敌机时，按 `docs/TEST_CHECKLIST.md` 扩展回归范围。
7. 测试失败必须区分“代码回归”“测试断言过期”“环境限制”，不能只写“测试通过”。
8. 版本规则变化必须同步修改断言和测试夹具；当前基线是 v0.9.0、100 个关卡、每 5 关一个 Boss、39 个光锥之外事件，且合成系统暂时停止开发、不对玩家开放。
9. 每次验证都记录在 `docs/TEST_RESULTS.md`，至少包含日期、版本或 commit、工作区状态、命令、设备/浏览器、验证流程、结果和环境限制。

## 文档规范

- 文档必须引用真实路径和真实命令；路径变更后立即同步。
- “已完成”只能表示当前代码和玩家界面确实可用；“实现但未开放”单独标注；“计划/建议/待确认”不得混写。
- 代码新增或修改完成后，更新 `docs/AI_HANDOFF.md`；根据影响更新架构、功能、数据、路线图、问题和测试文档。
- `CHANGELOG.md` 只写玩家可感知的最终版本内容。正式发布必须使用用户提供的版本号；修改前必须先把完整候选条目发给用户确认。
- `AI_HANDOFF.md` 的验证摘要必须注明对应的版本、commit 或工作区状态，不能把历史验证写成当前未提交工作区已验证。

## Git 规范

- 提交只包含当前任务相关变更，提交前检查 `git status --short`、`git diff --check` 和敏感文件。
- 默认本地提交，不自动推送或部署。
- 提交信息应简洁说明事实；文档任务使用 `docs:`，修复使用 `fix:`，功能使用 `feat:`。

## 发布目录时机

- 普通开发、修复和文档任务不强制生成 `publish-package/` 或 ZIP。
- 正式发布前必须运行 `package-release.ps1`，从当前源码重新生成发布目录和 ZIP，并检查其中包含最新入口、样式、`src/` 和 `assets/`。
- 发布目录和 ZIP 是被忽略的生成物，不提交到 Git；GitHub Pages 仍从 `main` 分支源码部署。

## 正式发布定义

- “正式发布”仅指用户明确提出发布要求并提供目标版本号。
- 用户确认该版本完整 `CHANGELOG.md` 条目后，才可继续检查、提交、推送 GitHub，并触发 `main` 分支的 Pages 工作流。
- 普通开发、文档同步、本地保存和测试不自动推送或部署。
