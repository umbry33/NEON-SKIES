# 技术决策记录

这里只记录会长期影响后续开发的选择；短期实现细节放在架构或任务记录中。

## ADR-001：保持原生静态 HTML + ES Modules

- 决策：不引入 npm、打包器、框架或后端；`index.html` 直接加载 `src/main.js`。
- 原因：项目是单页 Canvas 游戏，需要快速打开、手动发布和无依赖运行。
- 替代方案：Vite/React/TypeScript/服务端 API。
- 影响：浏览器直接承担模块加载；发布必须包含完整源目录；复杂度集中在原生 UI 和 `Game.js`。
- 何时可修改：只有当模块规模、类型安全、热更新或部署需求明确超过当前静态方案，并完成迁移计划与用户确认。

## ADR-002：15×15 固定核心网络

- 决策：核心固定在 `(7, 7)`，模块用 footprint 相对坐标占位，模块必须与核心连通。
- 原因：让空间构筑成为核心玩法，且配置码可以稳定编码位置。
- 替代方案：无限画布、动态尺寸或固定槽位。
- 影响：`ModuleSystem`、`UI`、玩家碰撞体、武器发射源和 `LoadoutCodec` 都依赖该几何。
- 何时可修改：只有在设计明确需要旋转、扩展网络或迁移存档协议时，必须保留旧码兼容策略。

## ADR-003：内容优先数据驱动

- 决策：模块、敌机、关卡、环境、事件、难度和连携优先放在 `src/config/`，行为通过系统工厂复用。
- 原因：新增内容不应修改所有实体和主循环分支。
- 替代方案：每个内容写一套类或在 `Game.js` 中硬编码。
- 影响：配置字段是长期 API；新增 behavior 仍需要系统、碰撞、绘制和测试协同。
- 何时可修改：只有当配置表达能力不足，且新增抽象能减少真实重复时。

## ADR-004：Canvas 几何绘制与 Web Audio 合成

- 决策：当前不依赖外部图片、字体或音频；图形由 Canvas 绘制，声音由 `SoundSystem` 合成。
- 原因：降低资源加载、版权、发布包和缺资源环境的风险。
- 替代方案：精灵图、音频文件、第三方音频库。
- 影响：视觉细节和音色由代码维护；引入外部资源必须保留后备并同步资源文档。
- 何时可修改：当正式美术/音频资源和加载失败策略确定后。

## ADR-005：手动编码的配置码与航程码

- 决策：普通机体使用 `LoadoutCodec`，光锥之外使用 `BeyondLightConeSystem.encode/decode`；不使用 `localStorage` 自动存档。
- 原因：允许玩家复制分享、跨会话恢复，同时保持静态项目无数据库。
- 替代方案：浏览器本地存储、服务器账户或完整 JSON 文件。
- 影响：ID、share code、字段版本和 checksum/解码逻辑必须长期兼容；编码不是加密安全机制。
- 何时可修改：只有在产品需要自动存档、账号同步或数据安全时，先设计版本迁移。

## ADR-006：生成发布包而非提交发布包

- 决策：`publish-package/` 与 ZIP 由 `package-release.ps1` 生成并被 `.gitignore` 忽略。
- 原因：避免源文件和发布副本漂移。
- 替代方案：把发布目录作为第二份源码提交。
- 影响：发布前必须重新生成和检查，不能把旧生成物当当前版本。
- 何时可修改：只有在引入可靠 CI 构建并明确产物保存策略后。
